## 0. Главная идея

Это Telegram-игра в формате чата.

Пользователь пишет игровые команды:

``` text
атака
защита
инвентарь
статус
...
```

Бот отвечает результатом действия.

Основной лимит:

-   после игрового действия ставится **КД 10 минут**;
-   если пользователь пытается выполнить действие во время КД, бот
    предлагает **пропустить КД за 1 Telegram Star**;
-   кнопка оплаты должна открывать **Telegram-платёж сразу после
    нажатия**;
-   бот не должен отправлять пользователю отдельное сообщение в личку;
-   после успешной оплаты бот автоматически выполняет **именно то
    действие, которое пользователь пытался выполнить**;
-   сразу после выполнения оплаченного действия снова ставится **КД 10
    минут**.

# 1. Условие доступа к игре

Перед игрой пользователь обязан один раз открыть личный чат с ботом и
отправить:

``` text
/start
```

После `/start` бот создаёт/активирует пользователя в БД.

В групповой чат пользователь после этого может играть обычными
сообщениями.

## Почему это обязательно

Личный `/start` нужен как факт взаимодействия пользователя с ботом и как
подготовка Telegram-аккаунта к дальнейшей работе.

В БД желательно хранить:

``` text
users
-----
id
telegram_id
username
first_name
created_at
last_start_at
is_active
```

Проверка перед игровым действием:

``` text
пользователь отправил /start?
    ↓
да → можно играть
нет → показать инструкцию
```

Сообщение:

``` text
🎮 Чтобы начать играть, сначала откройте личный чат с ботом и отправьте /start.
```

Можно сделать кнопку:

``` text
▶️ Открыть бота
```

с deep-link на личный чат.

# 2. Отдельный прогресс для каждого Telegram-чата

Очень важно: прогресс башни не должен быть глобальным для пользователя.

Один и тот же человек может играть:

``` text
Чат A → этаж 452
Чат B → этаж 17
Чат C → этаж 103
```

Поэтому игровой прогресс должен быть привязан минимум к:

``` text
telegram_user_id
chat_id
```

Например:

``` text
player_progress
---------------
id
user_id
chat_id
season_id
floor
hp
max_hp
attack
defense
class_id
checkpoint_floor
created_at
updated_at
```

Уникальный ключ:

``` text
(user_id, chat_id, season_id)
```

# 3. Сезон

Каждый месяц начинается новый сезон.

Например:

``` text
Season 1
01.10 — 31.10

Season 2
01.11 — 30.11
```

При начале сезона игрок выбирает класс.

Пример:

``` text
⚔️ Берсерк
🛡 Страж
🗡 Ассасин
🩸 Вампир
🧙 Арканист
🧠 Тактик
🃏 Шут
☠️ Некромант
```

Класс нельзя менять до конца сезона.

После окончания сезона:

-   башня начинается заново;
-   выбирается новый класс;
-   сезонные предметы/прогресс обновляются;
-   сохраняются достижения;
-   сохраняются коллекции;
-   сохраняются титулы;
-   сохраняется долгосрочная статистика.

# 4. Башня

Рекомендуемая структура сезона:

``` text
500 этажей
50 зон
10 этажей в каждой зоне
```

Каждый 10-й этаж --- босс.

Пример:

``` text
1–9   обычные события
10    БОСС

11–19 обычные события
20    БОСС

...

491–499 события
500   ФИНАЛЬНЫЙ БОСС
```

Не каждый этаж должен быть обычным боем.

Типы этажей:

``` text
⚔️ Бой
👹 Элита
💰 Сокровище
🛒 Торговец
🧩 Испытание
🔥 Риск/награда
🕯️ Событие
👑 Босс
```

# 5. Главное правило игрового действия

Каждое действие проходит через единый игровой pipeline.

Например пользователь пишет:

``` text
атака
```

Сервер делает:

``` text
1. Найти пользователя
2. Проверить /start
3. Найти прогресс в этом chat_id
4. Проверить сезон
5. Проверить КД
6. Если КД нет → выполнить действие
7. Посчитать результат
8. Сохранить результат
9. Поставить КД 10 минут
10. Отправить ответ
```

# 6. Если КД ещё не закончился

Например:

``` text
Игрок атаковал:
12:00

Следующее действие:
12:10
```

Игрок пишет:

``` text
атака
```

в 12:05.

Бот НЕ выполняет атаку.

Он отвечает примерно так:

``` text
⚔️ Вы ещё не готовы к следующему действию.

⏳ КД: 5 минут 12 секунд

⭐ Пропустить КД за 1 Telegram Star
```

И под сообщением должна находиться кнопка:

``` text
⭐ Оплатить 1 Telegram Star
```

# 7. Самое важное --- оплата Stars

Оплата должна работать именно как на примере игры «Рыбалочка».

Нельзя делать:

``` text
пользователь написал команду
↓
бот пишет в ЛС
↓
бот отправляет invoice
↓
пользователь оплачивает
```

Это НЕ нужная схема.

Нужная схема:

``` text
Пользователь пишет команду
        ↓
КД
        ↓
Бот отвечает в текущем чате
        ↓
[ ⭐ Оплатить 1 Telegram Star ]
        ↓
пользователь нажимает кнопку
        ↓
Telegram сразу открывает окно оплаты
        ↓
оплата
        ↓
бот получает подтверждение
        ↓
автоматически выполняет сохранённую команду
        ↓
КД снова 10 минут
```

То есть invoice должен быть **URL-инвойсом, созданным заранее кодом**, а
URL вставляется прямо в кнопку.

# 8. Как технически делать invoice

Для Telegram Stars использовать Telegram Bot API.

Нужен метод:

``` text
createInvoiceLink
```

Для Stars:

``` text
currency = "XTR"
```

Цена:

``` text
1 XTR
```

Провайдер платежей для Stars отдельно не нужен.

Концептуально сервер делает:

``` python
invoice_link = await bot.create_invoice_link(
    title="Пропуск КД",
    description="Мгновенно выполнить следующее действие",
    payload=payload,
    provider_token="",
    currency="XTR",
    prices=[
        LabeledPrice(
            label="Пропуск КД",
            amount=1
        )
    ]
)
```

После получения:

``` text
https://t.me/...invoice...
```

этот URL вставляется непосредственно в InlineKeyboardButton.

``` text

⭐ Пропустить КД за 1 Telegram Star
```

Кнопка:

``` text

```

При этом кнопка содержит:

``` text
url = invoice_link
```

То есть логика:

``` python
InlineKeyboardButton(
    text="⭐ Оплатить 1 Telegram Star",

```

``` text
/pay
```

или:

``` text
Оплатить
```

в личку делать не нужно.

# 10. Payload invoice

Нельзя просто создавать invoice без связи с конкретным действием.

В payload нужно зашифрованно/безопасно сохранить идентификатор операции.

Например:

``` text
skipcd:<payment_id>
```

А в БД создать:

``` text
pending_payments
----------------
id
telegram_user_id
chat_id
command
created_at
expires_at
status
invoice_payload
```

Пример записи:

``` text
id: 18392
telegram_user_id: 793216884
chat_id: -100123456789
command: атака
created_at: 12:05
expires_at: 12:15
status: pending
```

Payload:

``` text
skipcd:18392
```

------------------------------------------------------------------------

# 11. Почему нужно сохранять именно команду

Это ключевая механика.

Пользователь написал:

``` text
атака
```

Бот увидел КД.

Вместо простого:

``` text
КД есть
```

сервер создаёт pending action:

``` text
user = 123
chat = -100
action = "атака"
```

и создаёт invoice.

После успешной оплаты сервер получает:

``` text
payment_id = 18392
```

достаёт из БД:

``` text
user = 123
chat = -100
action = "атака"
```

и выполняет:

``` text
атака
```

автоматически.

Пользователю не нужно повторно писать команду.

# 12. Пример полного сценария

Пользователь:

``` text
атака
```

Сервер:

``` text
КД отсутствует
↓
выполнить атаку
↓
результат
↓
КД = 10 минут
```

Через 3 минуты пользователь:

``` text
атака
```

Сервер:

``` text
КД ещё 7 минут
↓
создать pending action
↓
создать invoice
↓
отправить сообщение с кнопкой
```

Сообщение:

``` text
⚔️ Вы ещё не готовы к следующей атаке.

⏳ Осталось: 7:00

⭐ Можно пропустить КД за 1 Telegram Star.
```

Кнопка:

``` text
⭐ Оплатить 1 Telegram Star
```

Пользователь нажимает.

Telegram:

``` text
┌────────────────────────┐
│ Оплатить 1 Telegram Star│
│                        │
│        ⭐ 1            │
│                        │
│        Оплатить        │
└────────────────────────┘
```

После оплаты Telegram сообщает боту об успешном платеже.

Сервер:

``` text
payment valid
↓
pending action valid
↓
action = атака
↓
выполнить атаку
↓
сохранить результат
↓
КД = 10 минут
↓
отправить результат в исходный chat_id
```

Например:

``` text
⚔️ Вы наносите удар!

👹 Страж Врат получает 184 урона.

❤️ HP босса: 816/1200

⏳ Следующее действие через 10 минут.
```

# 13. Очень важно: после оплаты НЕ делать повторный /command

Неправильно:

``` text
оплата
↓
бот ждёт, пока пользователь снова напишет "атака"
```

Правильно:

``` text
оплата
↓
автоматически execute(action)
```

То есть payment handler должен вызывать тот же игровой сервис, который
используется обычной командой.

Например архитектурно:

``` text
CommandHandler
      ↓
GameService.execute_action()
      ↑
PaymentService
```

Обычная команда:

``` text
"атака"
    ↓
GameService.execute_action()
```

Оплата:

``` text
successful_payment
    ↓
достать pending action
    ↓
GameService.execute_action()
```

Нельзя дублировать боевую логику в payment handler.

# 15. CooldownService

КД нельзя реализовывать просто через `setTimeout`.

КД должен храниться в БД.

Например:

``` text
cooldowns
---------
user_id
chat_id
action_type
available_at
```

Пример:

``` text
user_id = 123
chat_id = -100123
action_type = combat
available_at = 2026-10-06 01:44:00
```

Проверка:

``` text
now < available_at
```

→ КД активен.

Если:

``` text
now >= available_at
```

→ действие разрешено.

------------------------------------------------------------------------

# 16. После обычного действия

После успешного игрового действия:

``` text
available_at = now + 10 minutes
```

После оплаченного пропуска:

``` text
оплата
↓
execute action
↓
available_at = now + 10 minutes
```

То есть Stars не дают игроку бесконечно спамить.

Каждый пропуск разрешает **ровно одно действие**.

------------------------------------------------------------------------

# 17. Оплата должна быть идемпотентной

Это обязательный пункт.

Нельзя допустить:

``` text
одна оплата
↓
атака
↓
атака
↓
атака
```

Одна успешная транзакция = одно действие.

В таблице платежей:

``` text
payments
--------
id
telegram_payment_charge_id
user_id
chat_id
amount
currency
payload
status
created_at
```

Уникальный:

``` text
telegram_payment_charge_id
```

Если Telegram/сервер повторно обработает событие, оно не должно повторно
выполнить действие.

Алгоритм:

``` text
successful_payment
        ↓
проверить charge_id
        ↓
уже обработан?
   ↓           ↓
  да           нет
  ↓             ↓
STOP       обработать
              ↓
        execute action
              ↓
        mark as processed
```

------------------------------------------------------------------------

# 18. Проверять нужно абсолютно всё

При обработке оплаты:

``` text
1. Пользователь существует?
2. Пользователь когда-либо делал /start?
3. Payload существует?
4. Pending payment существует?
5. Payment ещё не использован?
6. Payment не истёк?
7. Telegram user совпадает?
8. chat_id совпадает?
9. Цена = 1 Star?
10. currency = XTR?
11. pending action всё ещё актуален?
12. Игрок всё ещё находится в этом чате?
```

Только после этого:

``` text
execute_action()
```

------------------------------------------------------------------------

# 19. Истечение invoice

Pending payment не должен жить вечно.

Например:

``` text
создан в 01:05
expires_at = 01:20
```

Если пользователь нажал старую кнопку через час:

``` text
❌ Этот платёж больше недействителен.
Попробуйте выполнить команду ещё раз.
```

Также можно сделать фоновой cleanup:

``` text
pending payments > 15 минут
→ expired
```

------------------------------------------------------------------------

# 20. Защита от двойного клика

Пользователь может нажать кнопку несколько раз.

Поэтому payment handler должен использовать транзакцию/блокировку.

Схема:

``` text
pending_payment.status = pending
```

при обработке:

``` text
pending → processing
```

После успешного выполнения:

``` text
processing → completed
```

Если уже:

``` text
completed
```

повторное выполнение запрещено.

------------------------------------------------------------------------

# 21. Самое важное правило для боёв

Оплата не должна менять результат боя напрямую.

Stars дают только:

``` text
право выполнить одно действие сейчас
```

То есть:

``` text
⭐ = пропуск КД
```

а не:

``` text
⭐ = дополнительный урон
⭐ = бесплатная победа
⭐ = гарантированный крит
```

Это намного лучше для баланса.

# 22. Адаптивный AI

Главная фишка игры --- противник изучает конкретного игрока.

Хранить:

``` text
behavior_profiles
-----------------
user_id
chat_id
attack_rate
defend_rate
aggression
predictability
recent_actions
after_big_damage
common_sequences
```

Пример:

``` text
Игрок:

атака → атака → защита → атака
атака → атака → атака
защита → атака
```

AI постепенно понимает:

``` text
после сильного урона игрок часто защищается
```

и начинает адаптироваться.

# 23. AI не должен быть идеальным

Если босс всегда знает действие игрока --- игра станет нечестной.

Пример:

``` text
Этаж 1–10
80% случайность
20% анализ

Этаж 11–30
50% случайность
50% анализ

Этаж 31–60
30% случайность
70% анализ

Этаж 61–100
20% случайность
80% анализ

Высокие этажи
10–20% случайность
80–90% анализ
```

Даже очень умный босс иногда ошибается.

# 28. Предметы класса

Предмет класса не должен быть бесполезным для остальных.

Правило:

``` text

→ доступен всем

→ только конкретному классу
```

Например:

``` text

+45 ATK
+ дополнительный бонус класса
```

Пример для Берсерка:

``` text

→ максимальный урон

→ лечение от урона
```

# 37. Что НЕ делать

## Не делать отдельную оплату в ЛС

Неправильно:

``` text

↓

↓
ЛС
↓
invoice
```

## Не просить повторно команду

Неправильно:

``` text
оплата
↓
"теперь напишите атаку"
```

## Не выполнять действие сразу после создания invoice

Неправильно:

``` text
создали invoice
↓
сразу атака
```

Атака должна выполняться только после подтверждённой оплаты.

## Не хранить КД только в памяти

После рестарта сервера КД должен продолжить работать.

## Не давать повторно использовать платёж

Каждый Telegram payment charge должен обрабатываться только один раз.

# 40. Финальная критически важная цепочка

Вся система должна в итоге работать именно так:

``` text
                 ПОЛЬЗОВАТЕЛЬ
                       │
                       ▼
                  /start в ЛС
                       │
                       ▼
                 Пользователь БД
                       │
                       ▼
                 Пишет команду
                       │
                       ▼
                Проверка КД
                  /         \
                нет          да
                │             │
                ▼             ▼
        Выполнить       Создать pending
         действие          action
                │             │
                ▼             ▼
          КД 10 минут    createInvoiceLink
                              │
                              ▼
                     Кнопка с invoice URL
                              │
                              ▼
                    ⭐ 1 Telegram Star
                              │
                              ▼
                      Telegram Payment
                              │
                              ▼
                    successful_payment
                              │
                              ▼
                    Проверка платежа
                              │
                              ▼
                   достать pending action
                              │
                              ▼
                  Выполнить его автоматически
                              │
                              ▼
                         КД 10 минут
```

## Главный принцип

**Telegram Stars не выполняют игровое действие сами по себе.**

Они дают пользователю право **один раз обойти текущий 10-минутный
cooldown**, после чего сервер самостоятельно выполняет ранее сохранённую
команду.

Именно поэтому оплата должна быть связана с конкретным:

``` text
user_id
+
chat_id
+
action
+
pending_payment
```

а не просто с абстрактным «пропуском КД».

Это позволит сделать систему безопасной, предсказуемой и полностью
автоматической.

# 41. Конфигурация боссов — не хардкодить каждого босса

Боссов должно быть много, поэтому нельзя делать:

```text
Boss1.ts
Boss2.ts
Boss3.ts
...
Boss1500.ts
```

Вместо этого нужна **конфигурационная система**.

Один универсальный движок читает конфиг босса и понимает:

- характеристики;
- способности;
- фазы;
- AI-поведение;
- слабости;
- сопротивления;
- части тела;
- правила адаптации;
- награды;
- NFT-шанс;
- уникальные условия.

Пример структуры:

```text
BossDefinition
├── identity
├── stats
├── biome
├── ai
├── body
├── abilities
├── phases
├── resistances
├── weaknesses
├── loot
├── behavior_rules
└── encounter_rules
```

# 43. Почему конфиг лучше отдельных классов

Движок остаётся один:

```text
CombatEngine
```

А босс меняется только конфигом:

```text
BossConfig
   ↓
CombatEngine
   ↓
BossAI
   ↓
CombatResult
```

Поэтому можно сделать 1500 боссов без 1500 разных реализаций.

Уникальность получается комбинацией:

```text
статы
+
AI
+
способности
+
фазы
+
части тела
+
слабости
+
условия
+
арена
+
лут
```

# 44. Конфигурация способностей

Каждая способность должна быть универсальным объектом.

Например:

```yaml
id: counter_stance
name: "Ответная стойка"

trigger:
  type: after_player_attack

conditions:
  - player_action_count_last_3 >= 2

effect:
  type: counter_attack
  damage_multiplier: 1.35
```

Другой пример:

```yaml
id: punish_defense
name: "Разрушитель щита"

trigger:
  type: player_defend

effect:
  type: defense_break
  value: 0.30
```

Ещё:

```yaml
id: adaptive_prediction
name: "Чтение противника"

trigger:
  type: before_turn

effect:
  type: increase_prediction
  value: 0.15
```

# 58. Как работает 5×5 поле

У босса есть виртуальная модель:

```text
       Голова
         ↑
   Левая рука   Правая рука

        Торс

   Левая нога  Правая нога
```

5×5 позволяет сделать расположение визуально более интересным.

Например:

```text
⬜ 🟥 🟥 🟥 ⬜
🟥 🟥 🟥 🟥 🟥
🟥 🟥 🟥 🟥 🟥
⬜ 🟥 🟥 🟥 ⬜
⬜ 🟥 🟥 🟥 ⬜
```

Красный `danger` — доступная зона.

Пустые клетки:

```text
не имеют callback_data
```

или используются как декоративные disabled-кнопки.

Они не должны реагировать на нажатие.

---

# 59. Почему нельзя просто написать «голова / тело / ноги»

Потому что игрок должен выбирать риск.

Например:

| Зона | Шанс попасть | Урон |
|---|---:|---:|
| Голова | 35% | ×1.60 |
| Торс | 75% | ×1.00 |
| Левая рука | 65% | ×0.75 |
| Правая рука | 65% | ×0.80 |
| Левая нога | 85% | ×0.55 |
| Правая нога | 85% | ×0.55 |

Получается:

```text
Голова
→ сложно попасть
→ огромный урон

Нога
→ легко попасть
→ небольшой урон

Торс
→ средний риск
→ стабильный урон
```

```text
      [ ][Л][Т][Т][П][ ]
```

# 61. Нажатие на часть тела

Игрок нажимает:

```text
голова
```

Сервер получает:

```text
callback_data =
combat:attack:boss_id:head:turn_id
```

Проверяет:

```text
пользователь
chat_id
turn_id
КД
бой
доступность клетки
```

После этого рассчитывает:

```text
hit = random() <= hit_chance
```

Если попал:

```text
damage =
base_attack
× body_multiplier
× crit_multiplier
× equipment_bonus
× class_bonus
× boss_modifiers
```

---

# 62. После выбора клетки

После нажатия выбранная клетка должна стать зелёной.

То есть:

```text
style = success
```

Например:

```text
голова → зелёная
```

Все остальные клетки остаются такими, как были.

После выбора нужно обновить inline keyboard через:

```text
editMessageReplyMarkup
```

или соответствующий метод библиотеки.

# 63. Цвета кнопок

В актуальном Telegram Bot API у `InlineKeyboardButton` есть `style`.

Поддерживаются:

```text
danger  → красный
success → зелёный
primary → синий
```

Telegram добавил `style` для `InlineKeyboardButton` в Bot API 9.4. citeturn0search1turn0search2

Поэтому для этой механики:

```text
доступная клетка:
style = "danger"

выбранная клетка:
style = "success"

нейтральная клетка:
без callback_data
```

# 64. Важный нюанс с библиотекой

Если используем библиотеку, в которой версия Telegram API ещё не поддерживает:

```text
style
```

нужно обновить библиотеку.

Если библиотека всё ещё не предоставляет это поле, можно сделать низкоуровневый вызов Bot API или обновить используемый Telegram SDK.

Не нужно пытаться имитировать красный цвет символами:

```text
🔴
```

если цель — именно цвет фона кнопки.

Telegram официально поддерживает `danger`, `success` и `primary` для inline-кнопок. citeturn0search1turn0search0

# 65. Неподвижные клетки

Клетки, которые не являются частью тела:

```text
⬜
```

не должны иметь:

```text
callback_data
```

То есть это обычные декоративные кнопки без действия либо другой безопасный вариант, который клиент не сможет нажать как игровую клетку.

Важно:

```text
кнопка выглядит частью поля
но
сервер не принимает её как игровое действие
```

И сервер всё равно должен проверять координату.

Нельзя доверять только интерфейсу.

# 74. Нельзя доверять callback_data

# 77. Начальный шанс NFT

В начале каждого сезона:

```text
nft_chance = 0.0001
```

То есть:

```text
0.0001 = 0.01%
```

Каждый пройденный босс немного увеличивает шанс.

Предлагаемая формула:

```text
nft_chance =
min(
    0.0001 + bosses_defeated * 0.000005,
    0.00035
)
```

Получается:

```text
После 0 боссов:
0.000100 = 0.0100%

После 10:
0.000150 = 0.0150%

После 20:
0.000200 = 0.0200%

После 30:
0.000250 = 0.0250%

После 40:
0.000300 = 0.0300%

После 50:
0.000350 = 0.0350%
```

Это всё ещё очень редкий дроп.

# 78. Сброс NFT-шанса

Каждый сезон:

```text
bosses_defeated = 0

nft_chance = 0.0001
```

То есть игрок не может бесконечно накапливать шанс между сезонами.

Например:

```text
Season 1
50 боссов
NFT chance = 0.035%

Season 2
снова:
NFT chance = 0.01%
```

Это создаёт дополнительную мотивацию проходить сезон полностью.

# 79. NFT roll

После убийства босса:

```text
boss defeated
      ↓
обычный loot
      ↓
relic roll
      ↓
NFT roll
```

NFT:

```typescript
const roll = Math.random();

if (roll < player.nftChance) {
    giveNftReward();
```

Но в production лучше использовать криптографически стойкий RNG, а не обычный `Math.random()` для ценных наград.

# 84. Важно: переносить instance, а не просто item_id

У предмета могут быть:

```text

улучшения
прокачка
рандомные статы
история
```

Поэтому сохранять:

```text

```

недостаточно.



без возможности перенести:

```text

золото

артефакты
все улучшения
```
